## 三、为什么后续要按这个顺序做

后续排序遵循一个很简单的原则：

1. 先把已经完成的成果彻底稳住
2. 再补那些已经实现但还不够完整的模块
3. 再做真实数据验收，确认不是只在合成数据上成立
4. 最后再继续扩展高价值算法能力

这样排有几个好处：

- 风险最低，不会一边继续加功能，一边把已有能力搞散
- 每一轮产出都能沉淀成稳定资产，而不是临时堆功能
- 后面如果换人接手，不需要重新判断哪些内容可信

如果反过来直接继续大规模新增算法，最容易出现的问题就是：

- 文档和程序行为不一致
- GUI 已有入口，但参数校验缺失
- 测试只覆盖 CLI，没有覆盖 GUI
- Release 能编译，但安装后的实际运行没人确认

所以当前最合理的策略仍然是：先收口，再扩展。

# 2026-05-10 复核结论（最新口径）

## 1. 当前产品定位

当前项目定位明确为 **GIS / 遥感算法工作台**，而不是全能 GIS 平台。GUI 的核心职责仍然是：

- 组织算法入口
- 管理参数填写与校验
- 执行任务、批处理与任务记录
- 提供日志、结果摘要与回归验证入口

因此，后续工作不再把“结果预览界面 / MapCanvas / 地图浏览能力”作为当前建设目标，也不再将其作为问题清单中的优先事项。

## 2. 本轮复核明确排除项

以下方向在本轮复核与执行中 **明确不纳入范围**：

- 结果预览界面、MapCanvas、地图浏览能力
- 围绕“做成全能 GIS 平台”的扩展性讨论
- 当前 `vcpkg` 组织方式的调整与再讨论

这三项不是本轮整改阻塞项，后续判断也不再把它们作为当前阶段问题来源。

## 3. 当前最重要的项目判断

结合源码、文档、测试入口与构建结构复核，当前项目已经明显越过“先把框架搭起来”的阶段，进入 **以稳定化、可维护性和结果可信度为主的工程深化阶段**。

可以继续维持不变的判断：

- 主执行链 `core / framework / plugins / cli / gui / tests` 已经成型
- 插件化参数驱动架构适合当前“算法工作台”定位
- 项目已经具备较强的回归意识和交付意识

当前真正需要优先处理的问题，已经不再是“功能有没有”，而是：

1. **复杂度控制**

   - 当前已有完整回归基础，但仍需更明确地区分提交级、夜间级、版本验收级验证
4. **大数据场景工程能力**
