# 影像裁切与镶嵌 / 栅格切片

## 功能说明

将栅格数据按 XYZ/TMS 标准 Web 地图瓦片方案切片，输出 `z/x/y.png` 目录结构，可直接部署为地图瓦片服务。

## 输入与输出

- 输入：单波段或多波段栅格
- 输出：瓦片目录（`z/x/y.png`）+ `metadata.json`

## 算法内容

栅格切片是将连续的栅格数据按 Web 地图标准瓦片网格分割为离散瓦片的过程。核心步骤包括：

1. **重投影**：目标坐标系恒为 EPSG:3857。`profile` 目前**只实现 `mercator`**；`geodetic` 与 `raster` 会显式失败（`tile profile "…" is not supported yet; only profile=mercator is implemented`），不会退回经纬度网格或原坐标系（枚举取值与实现面的不一致已挂账 N48）。
2. **分级但不物化金字塔**：整幅只重投影一次成 EPSG:3857 的中间数据集；zoom level 只用来确定索引网格，**每个层级不再各自物化一张全球降采样图**（该做法在 R-T17-7 已删除），每瓦片按反算读窗直接从中间数据集取块再缩放。
3. **瓦片编号**：起止行列号由 **EPSG:3857 度量范围**推导（`floor((x - worldMinX) / tileWidth)`），不做“度量→经纬度→索引”的往返；用户给的瓦片范围反而要先前向投影到 3857 再参与计算。XYZ 与 TMS 只差 y 的编号方向。
4. **透明处理**：将 NoData 像素转为 Alpha=0（完全透明），支持 PNG/WebP 格式输出。
5. **空白跳过**：不是“全透明”才跳 —— 瓦片内**不透明像元 ≤ 4** 即判为空并跳过（`kBlankOpaquePixelTolerance = 4`）。

与 QGIS "Generate XYZ tiles"、ArcGIS "Manage Tile Cache" 和 GDAL `gdal2tiles` 的核心算法一致。

### 自动 max_zoom 计算

Web Mercator 各层级地面分辨率：

```
resolution(z) = 2π × 6378137 / (tileSize × 2^z)
```

常数口径 = **球体**（不是 WGS84 椭球）：`a = 6378137`、`a·π = 20037508.342789244`、
`2π·a = 40075016.685578488`；世界包络与 `doTile` 里对度量范围的钳位都用同一个
`20037508.342789244`（`src/core/src/tile_grid.cpp` 的 `kMaxWebMercator`）。
写成 `20037508.34` 这类四舍五入口径再去配 `1e-3` 级容差会当场撞红 —— 同一族的印错
（`20037808.34`）与容差夹心在投影转换那篇里已实测过：`Δx@116° = 1.7975e-3 m > 1e-3`
（那条是批次 D 前一把的现跑读数，不是本篇用例的）。本篇的判据用的是像元列数量级（容差 1 列
= 611.5 m），常数口径本身判不到（挂账见 RELEASE 的 D1-C2 缺口清单）。
`tileSize = 256` 时 `resolution(0) = 156543.03392804097`，`tileSize = 128` 时是它的两倍
`313086.06785608194`。

自动计算：找到最大的 z 使得 `resolution(z) >= 输入栅格的地面分辨率 × 0.5`。两点前提正文必须交代：自动值与用户显式值最后都会被**硬钳到 22**（`maxZoom = min(maxZoom, 22)`）；而“输入栅格的地面分辨率”取的是**源 CRS 单位**下的像元大小，与上式的“米/像元”直接比较 ⇒ 源是地理坐标系（度）时这个自动值只有量级意义，应自行指定 max_zoom。

实现是 `computeMaxZoom(pixelSize, tileSize)`：**从 z=30 往下**遍历，第一个满足
`resolution(z) >= pixelSize × 0.5` 的 z 即返回，全都不满足才落回 0。那个 `× 0.5`
（“源半个像元”）单独决定边界档，去掉它会自动浅一层。两条手推实例（判据分别钉在
`PluginTest.TileAutoMaxZoomBandAndTilePixelSizeGrid` 与真实腿的 `cutting_tile` 用例上）：

| 夹具 `pixelSize` | `tileSize` | 阈值 `pixelSize × 0.5` | 命中档 | 上一层为何不命中 |
| --- | --- | --- | --- | --- |
| 1000 m | 256 | 500 | z = **8**（`resolution(8) = 611.496226281410`） | `resolution(9) = 305.748113140705 < 500` |
| 1000 m | 128 | 500 | z = **9**（同值 611.496226281410） | `resolution(10) = 305.748113140705 < 500` |
| 50 m | 256 | 25 | z = **12**（`resolution(12) = 38.218514142588`） | `resolution(13) = 19.109257071294 < 25` |
| 50 m | 128 | 25 | z = **13**（同值 38.218514142588） | `resolution(14) = 19.109257071294 < 25` |

### `tile_pixel_size` 的两处消费点

这个键在产品里被消费**两次**，且两处的作用不一样，只盯其中一处会漏掉另一处的缺陷：

1. **网格分辨率的除数**：`resolution(z)` 的分母含 `tileSize` ⇒ 它参与"自动 max_zoom 落哪一档"。
   由上表：`pixelSize=1000` 时 `256 → z=8` 而 `128 → z=9`；`pixelSize=50` 时 `256 → z=12` 而 `128 → z=13`。
   ⇒ **瓦片像素减半，自动档加深一层**（该层瓦片数在真实数据上仍是 1 张/层，只要源包络小于该层单瓦片米宽）。
2. **每瓦片的输出像元数**：瓦片内目标子矩形按 `tileResX = 瓦片地理宽 / tileSize` 放置
   ⇒ 同一段地理跨度在 `128` 档摊到的像元数恰是 `256` 档的一半。
   例：源东缘距瓦片西缘 64000 m、z=8 的单瓦片米宽 156543.03392804097 ⇒
   覆盖列数 = `64000 / 156543.03392804097 × tileSize` 向外取整，`tileSize=256` 得 105 列、
   `tileSize=128` 得 53 列；而 `tileSize=128` 配上自动档加深的 z=9（单瓦片米宽
   78271.51696402048，像元米距 `78271.5…/128 = 611.496226281410` 与 z=8/256 档的
   `156543.0…/256` 相同）就回到 105 列 —— 这两个"一半 / 复原"的关系合起来才证明 `tileSize`
   真的进了网格，而不只是当了输出画布的宽高。

注意：`tile_pixel_size` **不改变**某一层级单张瓦片覆盖的地理范围 —— 层级索引由
`tiles = globalWidth / tileSize = tileSize × 2^z / tileSize = 2^z` 推导，`tileSize` 被约掉。
把它当"网格尺寸"来断言会得到一条恒真的判据。

### `add_alpha` 与 `resample` 的缺省口径（易误读的两处）

- **`add_alpha` 缺省是 `true`**（`doTile` 里 `getParam<bool>(params, "add_alpha", true)`）。
  `true` 时 GDALWarp 带 `-dstalpha`，透明度取该 alpha 波段（**所有**颜色波段都无有效像元才透明）；
  `false` 时没有 dstalpha 波段，透明度退回"逐波段 NODATA 判据取 **AND**"（任一波段 NoData 就遮掉）。
  因此 `add_alpha` 的可见差别只在"多波段且只有部分波段 NoData"的源上出现。
  测试侧的历史坑：既有 Tile 用例公用的参数 helper 把 `add_alpha` 显式设成 `false`，
  所以**用该 helper 的用例一条都判不到缺省 `true` 这条路径**；本动作的 GOLD 证据用例
  （`PluginTest.TileAutoMaxZoomBandAndTilePixelSizeGrid`）不走 helper，缺省键一律不传。
- **`resample` 的实际缺省是 `average`，而参数面板显示的默认是 `nearest`** —— 这是**已知不一致**，
  不是笔误：`paramSpecs` 里 `resample` 的 default 写 `nearest`，而 `doTile` 读的是
  `getParam<std::string>(params, "resample", "average")`（源码内 B16 注释点名"GUI 面板显示的默认
  与实际缺省不同"）。改成 `nearest` 会一次性换掉所有既有 tile 产物的插值，归 B19 决策门，
  文档这里只把两值写清，不做"应该统一"的承诺。

### XYZ 与 TMS 的区别

| 方案 | y=0 位置 | 转换公式 |
| --- | --- | --- |
| XYZ | 左上角（北极） | 直接使用计算值 |
| TMS | 左下角（南极） | `y_tms = 2^z - 1 - y_xyz` |

## 处理流程

1. 打开输入栅格，读取空间参考、地理范围、分辨率。
2. 校验空间参考与地理参考：**三道闸按下面顺序**，任一不过即失败（目标坐标系恒为 EPSG:3857）：
   ① 没有 CRS ⇒ `tile input has no spatial reference; cannot project to EPSG:3857`；
   ② 有 CRS、但**取不到地理变换** ⇒ `tile input geotransform is missing; cannot map pixels to the projected grid`
      （批次 D Task 8 新增，排在 ① 之后、③ 之前）；
   ③ 变换取到了，但不是正北零旋转网格（x 像元大小 > 0、y < 0、旋转/斜切项为 0）⇒
      `tile requires a north-up pixel grid (x pixel size > 0, y pixel size < 0, rotation/skew terms must be zero)`。
   ②与③的文案不许合并、①与②的顺序不许换：改前 ② 那种输入是被 ③ 报出去的——GDAL 取不到变换时仍会把默认恒等式
   (0,1,0,0,0,1) 填进数组，于是用户被告知"你的栅格旋转了"，而它根本没有地理参考（判据：用例
   `TileNamesMissingGeotransformSeparatelyFromNorthUpAndNoCrs` 三臂）。
3. 若 max_zoom = -1，根据影像分辨率自动计算。
4. 将影像边界转换为 WGS84 经纬度范围。
5. 逐 zoom level：
   a. 计算该层级覆盖的索引网格范围（不物化该层级的全球影像）。
   b. （曾经这里是“对非最高层级用 GDALTranslate 降采样到全局像素尺寸”，R-T17-7 已删除该物化步骤。）
   c. 计算覆盖的瓦片行列号范围。
   d. 逐瓦片在中间数据集上反算读窗取块，缩放到**瓦片内的目标子矩形**（内部瓦片子矩形恰为整张；边缘部分覆盖的瓦片按覆盖比例放置，未覆盖的边留在透明上），NoData 转透明、编码输出。
6. 生成 metadata.json（TileJSON v3.0 格式）。
7. 只有 `webviewer=leaflet` 或 `all` 会生成 Leaflet 预览页；**`openlayers` 没有实现分支**（选了既不产出也不报错），该取值同样属 N48 的“枚举宽于实现”。

### metadata.json 格式

遵循 TileJSON v3.0 规范，包含瓦片方案的完整描述信息，可直接被 Leaflet、MapLibre、OpenLayers 等 Web 地图库加载。

## 结果解释

- 每个瓦片为 256×256（默认）像素的 PNG/JPEG/WebP/GeoTIFF 图像。
- NoData 区域为透明像素（Alpha=0）。
- 瓦片可直接部署到 Nginx/Apache 等 Web 服务器作为静态瓦片服务。

## 适用场景

- 将 DEM/卫星影像发布为 Web 地图底图。
- 生成离线地图瓦片包供移动端使用。
- 构建内部 GIS 瓦片服务。
- 大范围栅格数据的快速可视化预览。

## 推荐输出目录名

- `tiles_dem/`
- `tiles_satellite/`

## 注意事项

- 输入栅格必须**有空间参考**、**取得到地理变换**、且变换是 north-up 零旋转像元网格，三者缺一本动作**必然失败**（不是“可能失败”）。
- 大范围高分辨率影像的 max_zoom 会很高（如 18-22），瓦片数量指数增长；**max_zoom 无论自动还是手动都被硬钳到 22**，超过 22 的需求要换工具。
- mercator 剖面下纬度范围限制在 ±85.05°。
- 续切模式（resume）可中断后继续，仅生成缺失的瓦片。
- JPEG 格式不支持透明，若需透明背景请使用 PNG 或 WebP。
