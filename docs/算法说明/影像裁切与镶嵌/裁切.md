# 影像裁切与镶嵌 / 裁切

## 功能说明

按矩形范围或裁切矢量对输入栅格进行裁切。

## 输入与输出

- 输入：
  - 栅格：建议 `.tif`
  - 裁切矢量：常用 `.shp` `.gpkg` `.geojson`
- 输出：裁切后的栅格，建议 `.tif`

## 参数

| 参数 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| 输入文件 | 文件路径 | 是 | 无 | 输入栅格路径。 |
| 输出文件 | 文件路径 | 是 | 无 | 输出裁切结果。 |
| 范围 | 范围 | 否 | `0,0,0,0` | 格式 `xmin,ymin,xmax,ymax`；四个值全为 0 按"未提供范围"处理，此时必须给裁切线 |
| 裁切线 | 文件路径 | 否 | 无 | 用于裁切的矢量边界。 |

## 算法内容

裁切用于从输入栅格中截取局部区域。当前实现有两条真实处理路径：如果提供了裁切线，则按矢量边界裁切；如果没有裁切线但提供了范围，则按矩形窗口裁切。两者最终都会生成新的栅格输出。

## 处理流程

1. 读取输入栅格、输出路径、范围和可选裁切线。
2. 检查 `范围` 和 `裁切线` 至少填写一个，两者都缺时报错 `Either extent or cutline must be specified for clip`。
3. 如果提供了裁切矢量：
4. 组装 `cutline` 和 `crop_to_cutline` 参数。
5. 调用 GDALWarp 按矢量边界裁切输出。
6. 如果未提供裁切矢量但提供了范围：
7. 将 `xmin,ymin,xmax,ymax` 转成 `projwin` 参数顺序。
8. 调用 GDALTranslate 按矩形窗口裁切输出。
9. 生成新的裁切结果栅格。

## 处理逻辑

- `空间范围` 和 `裁切矢量` 至少要填一个。
- 如果提供 `裁切矢量`，优先走按矢量裁切。
- 如果只提供 `空间范围`，走矩形窗口裁切。
- `范围` 的轴序是 `xmin,ymin,xmax,ymax`：实现把四元组拼成 GDAL 的 `-projwin ulx uly lrx lry`
  时用的下标顺序是 `[xmin, ymax, xmax, ymin]`。把它当成 `{minx, maxx, miny, maxy}` 读会得到负高度的
  窗口并按失败返回（实测案文 `Clip by extent failed: Error: Computed -srcwin 1 2 -161659 -161659 has
  negative width and/or height.`）。
- 窗口按**整像元向下取整**对齐，输出的左上角是对齐后的像元边而不是请求值本身。例如源
  `GeoTransform = (116.0, 0.001, 0, 40.0, 0, -0.001)`（20×10 ⇒ 包框 x∈[116.000,116.020]、
  y∈[39.990,40.000]）与请求 `116.005,39.994,116.012,39.998`：起始列 `(116.005-116.000)/0.001 = 5`、
  起始行 `(40.000-39.998)/0.001 = 2`、宽 `7`、高 `4`、输出 Origin `(116.005, 39.998)`。
- **部分相交不裁剪**：产物尺寸就是**请求窗**的尺寸，源包框之外的像元补 `0`，而且**不写 NoData**
  ⇒ 下游无法把"补的 0"与"真的是 0 的数据"分开。上例请求 `115.998,39.988,116.012,39.998` 得到 14×10，
  其中只有 12×8 = 96 格来自源 ⇒ 该带的 Mean 是 `96×5/140 ≈ 3.42857`（夹具常量 5.0）。
- **完全不相交也不报错**：返回成功，产物是一张请求尺寸的全 0 图（左上角仍是 `(xmin, ymax)`）。
  调用方若要区分"裁空了"与"裁出来全是 0"，本动作现在给不出信号（已登记为缺口）。

## 结果解释

- 矩形裁切得到的是按给定范围截取的规则矩形栅格。
- 矢量裁切会以矢量边界为准生成结果，更适合行政区、样区或专题范围提取。
- 像元尺寸与源一致（`-projwin` 路径不重采样），因此输出宽 = `(xmax-xmin)/源像元宽` 取整、
  高 = `(ymax-ymin)/源像元高` 取整。

## 适用场景

- 影像局部区域提取、按行政边界裁切和分析范围准备。

## 填写示例

- 空间范围：`500000,3200000,510000,3210000`
- 裁切矢量：`D:/data/clip_boundary.gpkg`
- 推荐输出文件：`D:/out/clipped.tif`

## 输出说明

- 输出结果为裁切后的栅格文件。
- 建议优先使用 `.tif`，便于继续做栅格分析或在 GIS 软件中查看。

## 推荐输出文件名

- `裁切_result.tif`

## 注意事项

- 输出一般建议使用 `.tif`。
- `空间范围` 默认全零时会被视为未填写。
- 判据凭据（Debug）：`PluginTest.CuttingClipByExtentProducesExpectedWindow` 把窗钉成**数**而不是一串文本
  ——输出 `GeoTransform` 的 `gt[0]=116.005`（窗西界）、`gt[3]=39.998`（窗北界）、`gt[1]=0.001`、
  `gt[5]=-0.001`（像元尺寸含 y 的负号）与两枚斜置槽 `0.0`，再加窗内两角像元等于夹具常量 5.0；
  六枚期望全部由夹具 `adfGT` 字面量与 `extent` 手算，不从产物回填。另有两档把边界情况钉住：
  `…PartiallyOutsideSourcePadsZeroWindow`（14×10 + 四格"补 0 带/数据带"取样 + `Mean = 96×5/140`）与
  `…DisjointFromSourceProducesZeroFilledWindow`（按**实到**登记：成功 + 10×10 全 0）。
  取证两臂：把 `-projwin` 的两槽换成 `{minx,maxx,miny,maxy}` 读法 ⇒ 三条用例全红在成功位；
  把 ulx 多加一个像元（返回码仍是 0）⇒ 红在 `gt[0]`、宽高、像元值与 Mean 这些**数**上，
  后者才证明"值级判据真的在比较"，前者只证明用反轴序会被 GDAL 拒。
- 腿侧（`real_data_raster`）现在把窗**解析成数再比**：`cutting_clip` 判 `2×2×1` + `Mean=1` + `StdDev=0`，
  新 case `cutting_clip_asymmetric_window` 判 `3×4×1`（同一夹具、非方形 ⇒ 才可能看见轴序被写反）。
  ⚠ 限制照实登记：腿的夹具每格都是 `1`，所以 Mean/StdDev 判的是"这带确实是源数据且恒定"，
  **不判窗落在哪**；方形窗 `2×2` 本身是 x/y 反射不变量，位置与轴序只在单测侧判得到。
