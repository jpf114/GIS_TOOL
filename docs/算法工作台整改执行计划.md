## 2. 当前定位

当前项目定位为 **GIS / 遥感算法工作台**。

当前产品的核心价值不在地图浏览或通用 GIS 平台能力，而在：

- 统一封装多类 GIS / RS 算法
- 通过插件机制复用 CLI 与 GUI 执行链
- 通过参数驱动、批处理、任务记录和回归测试提升工程可交付性

这意味着，后续整改应优先服务于：

- 算法工作流稳定性
- 结果可信度
- 可维护性
- 大数据场景下的工程能力

---

## 3. 明确不纳入本轮范围的事项

以下事项在本轮整改中明确不纳入范围：

3. 当前 `vcpkg` 组织方式的调整、替换或再讨论

如果后续需要重新讨论这些事项，应作为新的独立议题，不混入当前整改主线。

## 4. 本轮复核后的主要问题

## 4.1 P0

### P0-1 `MainWindow` 与关键 GUI 入口继续膨胀

当前 [mainwindow.cpp](/D:/Code/MyProject/GIS_TOOL/src/gui/mainwindow.cpp) 已承担过多职责，包括：

- 动作显示名与描述配置
- 参数文案映射
- 动作可见参数 / 必填参数逻辑
- 执行前校验联动
- 批处理、拖拽、任务结果反馈

这会带来几个直接风险：

- 小改动更容易波及无关逻辑
- 动作展示逻辑与执行逻辑耦合过重
- 新动作继续接入时，文件复杂度会继续上升

### P0-2 结果可信度需要进一步制度化

当前项目已经有结果摘要、任务耗时、部分元数据和真实数据回归基础，但仍需继续统一：

- CRS / EPSG 摘要
- 范围、分辨率、NoData 等关键输出信息
- 关键参数快照
- 不同算法输出摘要的表达口径

当前目标不是做结果预览，而是让“执行成功”之外的结果更可复核、更可追踪。

### P0-3 回归与验收分层还需固化

当前项目已经具备较强回归能力，但仍需继续明确：

- 提交级验证跑哪些
- 夜间或阶段性验证跑哪些
- 版本验收前必须重跑哪些

这项工作主要是工程制度化，不是补新功能。

## 4.2 P1

### P1-1 继续外提动作元数据与参数说明规则

当前 `MainWindow` 中仍保留较多动作展示和说明映射。即使第一批完成外提，后续仍应继续推进：

- 动作展示名
- 动作说明
- 参数显示文本
- 动作级展示 / 必填规则

### P1-2 为大数据场景补基础设施

重点不是继续横向加功能，而是逐步补强：

- 分块处理
- 长任务日志
- 失败定位
- 批处理稳定性

### P1-3 建立性能与工程指标基线

当前功能回归较强，但性能基线仍可继续增强。后续建议逐步固化：

- 耗时基准
- 大数据集内存压力观测
- 关键算法吞吐变化趋势

## 4.3 P2

### P2-1 插件内部职责继续拆分

例如分类、部分栅格算法、复杂矢量处理后续都适合继续按子域拆分。

### P2-2 统一错误与摘要表达

让 CLI、GUI、日志、任务中心中的错误与结果摘要更一致。

### P2-3 建立模块成熟度视图

后续建议单独维护一个“模块成熟度视图”，区分：

- 已闭环
- 已实现但仍需补生产级验证
- 仅适合中小数据
