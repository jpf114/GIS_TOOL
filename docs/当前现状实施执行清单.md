# 当前现状实施执行清单

> 编写日期：2026-05-18
> 适用范围：`GIS TOOL`
> 前置约束：仅 Windows、仅算法工作台、全局 vcpkg + 仓库 vcpkg.json 依赖清单、单人维护优先

> **面向后续执行者：** 本清单用于把上位计划拆成可逐项落实、逐项验收的执行任务。所有任务默认遵循"范围冻结、精准修改、先验证后收口"的原则。

**目标：** 在不扩展产品边界的前提下，把当前仓库收口为稳定、可验证、可发布的 Windows 算法工作台基线。

**架构：** 先统一文档和发布口径，再收紧 GUI 主链与结果表达，随后整理测试入口和新能力定级，最后完成发布验收。整个过程不引入新的展示产品方向，不改现有依赖管理策略。

**技术栈：** C++、CMake、Qt、GDAL、SQLite、CTest、NSIS、全局 vcpkg + 仓库 vcpkg.json 依赖清单

1. 当前项目已经完成到什么程度

3. 哪些工作应优先推进，哪些工作明确不做

## 2. 当前现状结论

### 2.1 产品定位

当前项目定位明确为：

- Windows 下的 GIS / 遥感算法工作台
- 插件式算法组织方式
- 提供 CLI 和 GUI 双入口
- 不做地图展示平台
- 不以跨平台为当前目标

这意味着后续实施重点不是扩展产品边界，而是提高以下四项能力：

- 稳定性
- 可维护性
- 可验证性
- 可交付性

### 2.2 当前已具备的基础

当前项目已经具备以下核心基础：

- `core / framework / plugins / cli / gui / tests` 主链完整
- 插件接口、参数系统、结果模型已成体系
- CLI / GUI 统一走插件执行链
- 任务队列、批处理、结果预览、任务历史、SQLite 持久化已接入 GUI
- 安装目录与 NSIS 安装脚本已具备
- CI 已包含 Debug / Release 构建、测试和打包
- 依赖版本已由仓库内 `vcpkg.json` 与 `builtin-baseline` 锁定，通过全局 vcpkg 预装
- `build/debug` 当前可发现 405 个测试
- 本地安装产物可运行，`gis-cli --list` 可列出 13 个插件

### 2.3 当前项目阶段

项目已明显越过"搭框架"和"把功能先跑起来"的阶段，进入：

**功能闭环完成后的产品化收口阶段**

当前最重要的工作不再是继续横向堆新算法，而是：

1. 统一代码、文档、测试、发布口径
2. 收紧 GUI 主链和关键产品行为
3. 固化结果可信度和回归验收链路
4. 把当前工作区收口为稳定发布基线

## 3. 本轮实施的明确边界

### 3.1 明确纳入范围

- GUI 主链收口
- 文档口径统一
- 结果元数据与结果摘要统一
- 测试分层与发布验收基线整理
- 已接入新能力的正式定级
- Release 交付收尾

### 3.2 明确不纳入范围

以下事项在本轮计划中明确不做：

1. MapCanvas、地图浏览、空间展示型界面
2. 跨平台适配（Linux/macOS）
3. 依赖管理策略大改
4. 大规模新算法扩充
5. 以"重构更优雅"为目标的大范围代码重写

如果后续需要讨论这些事项，应作为独立议题单独立项，不混入当前实施主线。

---

## 4. 实施总原则

1. **先收口，再扩展**
   当前阶段优先保证已有能力稳定、文档一致、测试可信。

2. **只做与当前目标直接相关的修改**
   不因为顺手就扩展产品边界。

3. **优先降低维护风险**
   单人维护条件下，复杂度控制优先级高于"功能更多"。

4. **所有阶段均以验证闭环为目标**
   每个阶段都必须有明确验收命令或验收结果。

5. **保持现有全局 vcpkg 依赖策略不变**
   当前依赖版本已经由仓库内 `vcpkg.json` 锁定，不在本轮再调整依赖管理模式。

---

## 5. 执行规则

- 每个阶段结束前都要留下明确产出，不能只有"改过了"的口头状态。
- 每次提交只覆盖一个清晰主题，不把文档、GUI 主链、结果元数据、发布收尾混成一个大改动。
- 不处理以下范围外事项：
  - 地图展示界面
  - Linux / macOS 适配
  - 依赖管理策略重构
  - 大规模新增算法
  - 仅为了"代码更优雅"的大重构
- 如果某阶段发现新增问题，先判断它是否阻塞当前阶段验收；不阻塞则记录到后续清单，不顺手扩散。

## 13. 推荐提交拆分

建议至少拆成以下 5 组提交，避免一次性混入过多变化：

1. 文档口径统一
2. GUI 主链收口
3. 结果元数据与摘要统一
4. 测试入口整理与新增验证
5. 新能力定级与发布收尾

---

## 14. 阻塞判断规则

以下问题视为阻塞，必须在对应阶段内处理：

- 文档描述与当前产品边界直接冲突
- GUI 主链出现明显功能回退
- 关键真实回归不稳定或结果解释不一致
- 发布前标准验证命令无法复用
- 安装产物无法正常运行

以下问题默认不阻塞当前阶段，可记入后续计划：

- 局部代码风格不一致
- 非主链性能优化
- 与当前发版无关的小型重构
- 新想法型增强需求

## 15. 风险与应对

| 风险 | 影响 | 应对方式 |
|------|------|---------|
| GUI 主链继续膨胀 | 后续修改成本快速上升 | 先做阶段 1，优先外提共享元数据与规则 |
| 文档口径继续漂移 | 版本判断混乱 | 阶段 0 统一边界和发布口径 |
| 元数据表达不统一 | 真实数据验收难复用 | 阶段 2 建立统一摘要口径 |
| 测试很多但发布时不会用 | 发布风险上升 | 阶段 3 明确验证入口分层 |
| 新能力状态不清 | 文档承诺超过实际 | 阶段 4 明确定级 |
| 收口过程中顺手扩需求 | 项目范围失控 | 严格遵守第 3 章边界，不做无关扩展 |
