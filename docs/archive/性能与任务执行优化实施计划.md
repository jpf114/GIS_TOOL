# 性能与任务执行优化实施计划

## 1. 背景

当前项目的 GUI 执行链已经把算法执行放到了工作线程里，所以"算法直接跑在主线程导致界面必然卡死"不是主要矛盾。更现实的问题主要有 4 类：

1. 取消只是表层动作  
   用户点了取消，但很多插件内部没有周期性检查，任务仍会继续占用 CPU、内存和磁盘 IO。

2. 进度更新过密  
   高频 `progress/log` 信号会增加跨线程 UI 刷新负担，界面会显得忙、抖、响应差。

3. 当前模型本质上还是单任务模型  
   现在更适合"后台跑一个任务"，还不适合直接扩成稳定的多任务调度系统。

4. 并发执行边界还不清楚  
   插件实例、进度归属、任务状态、资源上限这些问题没先收敛，多任务很容易把问题放大。

## 2. 本轮目标

本轮只做高收益、低风险改造：

1. 打通真实取消链路
2. 给进度上报做节流
3. 补最必要的自动化测试

本轮明确不做：

1. 多任务 UI
2. 任务队列
3. 插件实例隔离重构
4. 真实数据专项回归

## 3. 设计原则

1. KISS  
   只改当前最值钱的问题，不做完整任务系统重构。

2. 小步快跑  
   先把取消和进度收敛，再考虑任务模型升级。

3. 复用现有执行链  
   保留 `ExecuteWorker + QThread + QtProgressReporter + ProgressDialog`。

4. 先把单任务体验做好  
   单任务都不稳时，不直接上多任务。

## 4. 分阶段计划

### 阶段 1：协作式取消 ✅ 已完成

目标：用户点击取消后，任务能在合理时间内结束。

实施点：

1. 公共层提供统一取消语义 — `CancelledException` + `Result::cancelled()`
2. 公共层提供轻量取消检查入口 — `ProgressReporter::throwIfCancelled()`
3. 在所有插件的 `onProgress` 调用点前插入取消检查
4. GUI 执行链统一把取消结果转成一致状态

验收标准：

1. 长任务可提前结束 ✅
2. 返回结果明确标识为取消（`Result::cancelled` 字段）✅
3. 不再出现"界面显示取消但后台仍长时间继续执行" ✅

### 阶段 2：进度节流 ✅ 已完成

目标：减少高频 UI 刷新负担。

实施点：

1. 进度增量阈值（1%）
2. 时间间隔阈值（50ms）
3. 首次/完成/重置后的关键更新强制发出

验收标准：

1. 高频循环中的进度发射次数明显下降 ✅
2. 进度条仍连续、稳定 ✅
3. GUI 响应优于改造前 ✅

### 阶段 3：单任务状态模型收敛

本轮不实现，只保留后续方向：

1. 统一任务状态
2. 统一成功/失败/取消流转
3. 逐步把 UI 状态从执行细节中解耦

### 阶段 4：多任务与资源调度

本轮不实现，只保留后续方向：

1. 任务历史 / 串行队列
2. 任务切换 UI
3. 真正并发前先解决插件隔离、独立 reporter、资源上限
