## 一、项目现状

### 1.1 项目定位

GIS TOOL 是一个基于 **C++17 + GDAL + OpenCV + PROJ + Qt6** 的**插件式 GIS/遥感算法工作台**，提供 CLI 和 GUI 双入口，底层共享同一套算法插件引擎。当前工作区版本 **v1.0.0**，MIT 开源协议，仅支持 Windows 平台。

项目明确自定位为**算法工作台**而非全能 GIS 平台——核心职责是组织算法入口、管理参数填写与校验、执行任务与批处理、提供日志/结果摘要与回归验证入口。

### 1.4 插件系统

插件系统是整个架构的核心设计：

- **IGisPlugin 接口**：纯虚基类，定义 `name()`, `displayName()`, `version()`, `description()`, `paramSpecs()`, `execute()` 六个核心方法
- **GIS_PLUGIN_EXPORT 宏**：跨平台导出宏，每个插件 DLL 通过 `createPlugin()` / `destroyPlugin()` 两个 C 导出函数被加载
- **PluginManager**：扫描 `plugins/` 目录加载动态库，通过导出符号实例化插件对象

### 1.5 参数系统

参数系统是三层共享（CLI/GUI/底层）的核心设计：

- **ParamType 枚举**：String, Int, Double, Bool, FilePath, DirPath, Enum, Extent, CRS 共 9 种参数类型
- **ParamValue**：`std::variant<string, int, double, bool, vector<string>, array<double,4>>`，动态承载参数值
- **ParamSpec**：包含 key、displayName、description、type、required、defaultValue、minValue/maxValue、enumValues，并提供 Builder 风格的链式设置方法
- **tryParseParamValue**：统一解析字符串到类型化参数值，含中文错误提示
- **validateParams / validateParamValue**：统一参数校验逻辑，含范围检查、枚举校验、必填校验

### 1.7 进度与取消机制

- **ProgressReporter**：抽象接口，`onProgress()`, `onMessage()`, `isCancelled()`, `throwIfCancelled()`
- **CancelledException**：继承 `std::runtime_error`，协作式取消机制
- **CliProgress**：CLI 侧实现，不支持取消
- **QtProgressReporter**：GUI 侧实现，带进度节流（增量 1%、间隔 50ms）和 atomic 取消标志
- 全部 13 个插件、39 个文件、461 处取消检查已接入

## 二、架构优势

### 2.1 插件化架构成熟

`IGisPlugin` 接口 + `PluginManager` 动态加载，新增算法只需实现插件接口，无需修改框架代码。13 个插件已验证此架构的可扩展性。

### 2.2 参数系统统一

`ParamSpec` + `ParamValue` 三层共享（CLI/GUI/底层），9 种参数类型覆盖完整。`ParamSpec` 同时是 CLI、GUI 和文档的参数元数据权威来源。

### 2.3 协作式取消全链路贯通

`CancelledException` + `throwIfCancelled()` + 461 处取消检查，全部 13 个插件已接入。GUI 侧通过 `atomic<bool>` 取消标志 + 非模态 ProgressDialog 实现流畅的取消体验。

### 2.4 进度节流机制

`QtProgressReporter` 内置节流逻辑（增量 1%、间隔 50ms、关键更新强制发出），避免高频 UI 刷新。

### 2.5 任务管理系统

SQLite 持久化（按 displayGroup 分库、WAL 模式）、TaskRunner 统一调度、QTabWidget 任务中心、QtProgressReporter 按任务独立实例。

### 2.6 完整的测试与回归体系

364/364 自动化测试 + 173 项 GUI 自动化 + 真实数据专项回归（matching/raster/vector 三大方向 Debug + Release 双侧通过）。

### 2.7 文档体系完善

121 篇算法说明文档 + 架构文档 + 用户手册 + 多份规划文档，且已逐篇核对 ParamSpec 与文档差异。

## 三、当前存在的问题

### 🔴 P0 级（产品可用性阻塞）

#### 3.1 缺乏基础结果可视化

用户执行完算法后，**必须切换到外部工具（QGIS/ArcGIS）才能查看结果**，这直接切断了核心价值链。作为算法工作台，基础的结果确认能力（栅格缩略图、直方图、矢量轮廓、统计表格）是刚需。

**当前状态**：执行完成后仅在 ProgressDialog 中显示成功消息和输出路径，无法直观确认结果是否正确。

**期望方案**：在执行结果区域增加"查看结果"按钮，点击后切换执行页为结果预览页，展示基础可视化内容（缩略图、直方图、统计信息等），不做 MapCanvas 级别的地图浏览。

#### 3.2 大数据处理工程能力不足

当前缺乏分块处理基础设施。对于超过内存的大影像（如高分卫星全幅），现有实现可能直接 OOM 或性能急剧下降。GIS 行业中，GB 级数据处理是常态。

**具体表现**：
- 大影像（>2GB）全量读入内存可能 OOM
- 无分块读写机制
- 无内存使用监控与预警
- 长任务稳定性未充分验证

#### 3.3 CI/CD 严重不完善

- **无 vcpkg 缓存**：每次 CI 从零 `git clone vcpkg` + `vcpkg install` 全部依赖，构建时间极长（预计 30-60 分钟）
- **Release 测试仅 5 个用例**：与 Debug 全量 364 个差距巨大，Release 质量无保障
- **无自动发布流程**：没有 release artifact 上传，无安装包生成

### 🟡 P1 级（产品竞争力影响）

#### 3.4 版本号不一致

- `CMakeLists.txt` 和 `vcpkg.json` 当前版本均为 `1.0.0`
- `vcpkg.json` 版本仍为 `0.5.0`

应同步更新。

#### 3.5 缺乏元数据透传

处理后影像丢失原始元数据（传感器信息、采集时间、太阳角度等）。遥感数据链路的完整性要求处理结果能追溯到原始数据和所使用的算法参数。

**具体表现**：
- 辐射定标后的影像不保留原始增益/偏移信息
- 大气校正后不记录校正方法与参数
- 分类结果不记录分类器类型与训练参数

#### 3.6 缺乏工作流编排能力

GIS 处理通常是多步骤流水线（辐射定标 → 大气校正 → 裁切 → 分类 → 统计），当前每次只能手动执行单个算法，无法将常用流程编排为工作流模板。

**具体表现**：
- 多步骤处理需手动逐个执行，中间结果路径需手动填写
- 常用处理流程无法保存为模板
- 上一步输出无法自动传递到下一步输入

#### 3.7 缺乏分类精度评估

分类统计插件提供了 SVM/随机森林/最大似然分类，但缺少分类精度评估（混淆矩阵、Kappa 系数、OA/PA/UA），这在遥感分类中是标准验证环节。

#### 3.8 批量处理增强需求

当前批处理是目录级串行执行，缺乏：
- 参数模板（对同一目录下不同文件使用相同参数）
- 进度聚合（整体进度而非单个文件进度）
- 错误汇总（部分失败不影响整体继续，最终汇总报告）

### 🟢 P2 级（产品体验优化）

#### 3.9 缺乏用户引导/帮助系统

新用户面对 124+ 子功能，缺乏引导式操作流程、使用案例推荐和上下文帮助。

#### 3.10 缺乏日志级别控制与导出

当前日志系统较简单，缺乏分级（DEBUG/INFO/WARN/ERROR）和导出功能，排查问题困难。

#### 3.11 缺乏性能基准与资源监控

没有算法执行时间/内存占用的基准数据，用户无法评估处理效率，也无法发现性能退化。

#### 3.12 缺乏错误恢复机制

- 任务失败后无自动重试
- 长时间运行任务崩溃后无断点续做
- 中间结果不持久化，失败后从头开始

#### 3.13 点云模块依赖阻塞

当前 GDAL 3.12.3 的点云驱动为 `<none>`，vcpkg 安装目录下无 PDAL 头文件或运行库。点云功能无法在当前依赖条件下推进。

## 四、GIS 行业专家建议

### 4.1 产品定位：从"算法能力集合"到"工作台方案"

当前项目已经具备完整的**算法工作台**基础，但离稳定发布产品还有关键一步——**场景化封装与主链收口**。GIS 用户需要的不是孤立的"坡度计算"，而是可直接复用的"地形分析工作方案"。

**建议定义 3-5 个核心场景模板**：

1. **遥感预处理流水线**：辐射定标 → 大气校正 → 正射校正 → 裁切
2. **地形分析工作流**：DEM → 填洼 → 流向 → 汇流累积 → 河网 → 流域
3. **变化检测流程**：配准 → 变化检测 → 分类统计
4. **植被监测流程**：光谱指数计算 → 分类 → 分区统计

### 4.2 算法能力补充建议

#### 高优先级（行业刚需，当前缺失）

| 能力 | 说明 | 行业价值 |
|------|------|---------|
| 基础结果可视化 | 栅格缩略图、直方图、矢量轮廓、统计表格 | 核心价值链闭环 |
| 分类精度评估 | 混淆矩阵、Kappa 系数、OA/PA/UA | 遥感分类标准验证环节 |
| 元数据透传 | 处理后保留源文件 CRS、算法信息、关键参数 | 遥感数据链路完整性 |
| 时间序列支持 | 多时相数据堆叠、差值、趋势分析 | 变化检测与监测基础 |
| 栅格计算器增强 | 条件表达式、嵌套运算 | 用户最常用的栅格工具 |

#### 中优先级（差异化竞争力）

| 能力 | 说明 |
|------|------|
| 点云处理 | 依赖阻塞（GDAL 无点云驱动/PDAL），但这是行业趋势，必须突破 |
| 空间插值 | IDW、克里金、样条函数（从点数据生成连续面） |
| 影像融合增强 | Gram-Schmidt、PCA、IHS 等专业方法 |
| 网络分析 | 最短路径、服务区分析、设施选址 |

#### 低优先级（锦上添花）

| 能力 | 说明 |
|------|------|
| 深度学习推理 | 语义分割/目标检测已是遥感主流，建议预留接口 |
| 制图输出 | 地图布局、图例、比例尺、标注 |
| 数据库连接 | PostGIS/GeoPackage 直接读写 |
| 脚本扩展 | Python/Lua 绑定，允许用户自定义处理流程 |

| 维度 | QGIS | WhiteboxTools | GIS_TOOL |

### 4.4 架构演进建议

#### 4.4.1 基础结果可视化

不做 MapCanvas 全功能，提供**轻量级结果摘要视图**。在执行结果区域增加"查看结果"按钮，点击后切换当前执行页为结果预览页：

```
执行完成后：
├── 执行结果区域增加"查看结果"按钮
├── 点击后切换执行页为结果预览页
├── 栅格结果：
│   ├── 缩略图（降采样渲染，支持波段组合选择）
│   ├── 直方图（各波段值分布）
│   ├── 统计信息（范围/分辨率/波段数/NoData/值域/CRS）
│   └── "在外部打开"按钮 → 调用系统关联程序
├── 矢量结果：
│   ├── 几何轮廓缩略图
│   ├── 要素数量 + 几何类型
│   ├── 属性表前 N 行
│   └── 范围 + CRS
├── 统计结果：
│   ├── JSON/CSV 结果的表格化展示
│   └── 关键指标高亮
└── "返回参数"按钮 → 切换回参数填写页
```

#### 4.4.2 工作流引擎

在插件系统之上增加一层**工作流编排**：

```cpp
struct WorkflowStep {
    std::string pluginName;
    std::string actionKey;
    std::map<std::string, ParamValue> params;
    std::map<std::string, std::string> inputMapping;  // 上一步输出 → 当前输入
};

class Workflow {
    std::vector<WorkflowStep> steps;
    bool execute(ProgressReporter& progress);
};
```

这不需要大改架构，只需在框架层增加一个 `WorkflowRunner`，复用现有插件的 `execute()` 方法。

#### 4.4.3 元数据链路

当前 `Result` 的 `metadata` 字段是 `map<string,string>`，但缺乏结构化元数据标准。建议定义：

```cpp
struct ProcessingMetadata {
    std::string sourceFile;
    std::string sourceCrs;
    std::string processingAlgorithm;
    std::string processingVersion;
    std::string processingTime;
    std::map<std::string, std::string> algorithmParams;
};
```

并确保每个插件的输出文件都通过 GDAL Metadata 写入这些信息，形成**可追溯的处理链**。

#### 4.4.4 分块处理基础设施

```cpp
class RasterBlockProcessor {
public:
    struct Block {
        int xOff, yOff, xSize, ySize;
    };

    void process(const std::string& inputPath,
                 const std::string& outputPath,
                 std::function<void(const Block&, GDALRasterBand*, GDALRasterBand*)> fn,
                 ProgressReporter& progress);
};
```

这是解决大数据问题的根本方案，建议作为 P0 基础设施先行建设。

### 4.5 CI/CD 缓存方案说明

当前 CI 每次从零 `git clone vcpkg` + `vcpkg install` 全部依赖，构建时间极长。**缓存**是指在 CI 流水线中，将已安装的 vcpkg 依赖持久化到 GitHub Actions 的缓存中，后续构建直接复用，仅当依赖变更时重新安装。

**具体方案**：

```yaml
# GitHub Actions 缓存配置示例
- name: Cache vcpkg
  uses: actions/cache@v4
  with:
    path: |
      ${{ github.workspace }}/vcpkg
      ${{ github.workspace }}/vcpkg_installed
    key: vcpkg-${{ runner.os }}-${{ hashFiles('vcpkg.json') }}
    restore-keys: |
      vcpkg-${{ runner.os }}-
```

**缓存策略**：

| 策略 | 说明 |
|------|------|
| 缓存键 | 基于 `vcpkg.json` 的哈希值，依赖变更时自动失效 |
| 缓存路径 | vcpkg 安装目录 + installed 目录 |
| 恢复优先级 | 精确匹配 → 前缀匹配 → 全新安装 |
| 预期效果 | 首次构建 30-60 分钟，后续构建 5-10 分钟 |

**其他 CI 改进**：

| 改进项 | 说明 |
|--------|------|
| Release 全量测试 | 将 Release 测试从 5 个扩展到全量 364 个 |
| 构建产物上传 | Release 构建完成后上传 zip 安装包到 GitHub Release |
| 定时构建 | 每日定时触发全量构建 + 测试，及时发现退化 |

### 5.2 成熟度判断原则

1. 底层实现是不是已经有了

3. 是不是 GUI 已有，但参数校验不完整
4. 是不是实现和测试都有，但文档缺失

### 5.3 项目整体判断
