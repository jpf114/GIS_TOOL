# 基于当前现状的实施计划

> 编写日期：2026-05-18
> 适用范围：`GIS TOOL`
> 约束条件：仅 Windows 平台、仅算法工作台、继续使用仓库锁定的 `vcpkg manifest`、单人维护优先

> 状态更新（2026-05-18）：文档主入口、发布说明、架构文档、用户手册与算法总览已完成一轮收口；当前剩余主线工作集中在 GUI 主链、结果摘要一致性、测试分层与发布前完整验收。

---

## 1. 文档目的

本计划用于承接当前项目现状，给出一份可直接执行的实施路线，而不是重新定义产品方向。

本计划聚焦以下问题：

1. 当前项目已经完成到什么程度
2. 下一阶段最值得做的事情是什么
3. 哪些工作应优先推进，哪些工作明确不做
4. 如何用最小风险把当前工作区收口到稳定可发布状态

---

## 2. 当前现状结论

### 2.1 产品定位

当前项目定位明确为：

- Windows 下的 GIS / 遥感算法工作台
- 插件式算法组织方式
- 提供 CLI 和 GUI 双入口
- 不做地图展示平台
- 不以跨平台为当前目标

这意味着后续实施重点不是扩展产品边界，而是提高以下四项能力：

- 稳定性
- 可维护性
- 可验证性
- 可交付性

### 2.2 当前已具备的基础

当前项目已经具备以下核心基础：

- `core / framework / plugins / cli / gui / tests` 主链完整
- 插件接口、参数系统、结果模型已成体系
- CLI / GUI 统一走插件执行链
- 任务队列、批处理、结果预览、任务历史、SQLite 持久化已接入 GUI
- 安装目录与 NSIS 安装脚本已具备
- CI 已包含 Debug / Release 构建、测试和打包
- 依赖版本已由仓库内 `vcpkg.json` 与 `builtin-baseline` 锁定
- `build/debug` 当前可发现 405 个测试
- 本地安装产物可运行，`gis-cli --list` 可列出 13 个插件

### 2.3 当前项目阶段

项目已明显越过“搭框架”和“把功能先跑起来”的阶段，进入：

**功能闭环完成后的产品化收口阶段**

当前最重要的工作不再是继续横向堆新算法，而是：

1. 统一代码、文档、测试、发布口径
2. 收紧 GUI 主链和关键产品行为
3. 固化结果可信度和回归验收链路
4. 把当前工作区收口为稳定发布基线

---

## 3. 本轮实施的明确边界

## 3.1 明确纳入范围

- GUI 主链收口
- 文档口径统一
- 结果元数据与结果摘要统一
- 测试分层与发布验收基线整理
- 已接入新能力的正式定级
- Release 交付收尾

## 3.2 明确不纳入范围

以下事项在本轮计划中明确不做：

1. MapCanvas、地图浏览、空间展示型界面
2. 跨平台适配（Linux/macOS）
3. 依赖管理策略大改
4. 大规模新算法扩充
5. 以“重构更优雅”为目标的大范围代码重写

如果后续需要讨论这些事项，应作为独立议题单独立项，不混入当前实施主线。

---

## 4. 实施总原则

1. **先收口，再扩展**
   当前阶段优先保证已有能力稳定、文档一致、测试可信。

2. **只做与当前目标直接相关的修改**
   不因为顺手就扩展产品边界。

3. **优先降低维护风险**
   单人维护条件下，复杂度控制优先级高于“功能更多”。

4. **所有阶段均以验证闭环为目标**
   每个阶段都必须有明确验收命令或验收结果。

5. **保持现有 manifest 依赖策略不变**
   当前依赖版本已经由仓库内 `vcpkg.json` 锁定，不在本轮再调整依赖管理模式。

## 阶段 1：GUI 主链收口

### 目标

降低 `MainWindow` 和任务主链继续膨胀的风险，稳定当前最活跃的产品行为。

### 背景判断

最近提交已表明当前最频繁变动区域集中在：

- `MainWindow`
- 任务中心
- 参数回填
- 重跑 / 复编辑
- 批处理
- 离屏 GUI 回归

因此当前最应该优先收口的是 GUI 主链，而不是继续扩新功能。

### 主要任务

1. 持续外提 `MainWindow` 中的共享 GUI 元数据
   - 动作显示名
   - 动作描述
   - 分组展示规则
   - 参数说明文案
   - 可见性和规则性配置

2. 收紧参数自动联动逻辑
   - 自动输出路径
   - `extent`
   - `layer`
   - `expression`
   - 多输入 / 多文件参数行为

3. 收紧任务中心交互
   - 重跑任务
   - 复编辑任务
   - 删除任务
   - 清理历史
   - 清理日志

4. 收紧批处理主链
   - 目录扫描
   - 过滤规则
   - 提交计数
   - 成功 / 失败统计
   - 进度更新

### 涉及文件

- `src/gui/mainwindow.cpp`
- `src/gui/gui_data_support.h`
- `src/gui/gui_data_support.cpp`
- `src/gui/task_center_page.h`
- `src/gui/task_center_page.cpp`
- `src/gui/task_runner.h`
- `src/gui/task_runner.cpp`
- `tests/test_mainwindow.cpp`
- `tests/test_gui_support.cpp`

### 完成标准

- `MainWindow` 中与动作元数据直接相关的逻辑继续减少
- GUI 主链行为不发生功能回退
- 相关 `MainWindowTest` 与 GUI 离屏回归通过

## 阶段 4：工作流、日志、性能能力定级

### 目标

对当前已经进入工作区的新能力做明确处理，避免“代码有了，但产品地位不清”。

### 需要定级的能力

1. `Workflow`
2. `Logger`
3. `PerformanceMonitor`

### 主要任务

1. `Workflow` 定级
   - 如果作为 v1 正式能力：补参数约束、补测试、补文档

   - 如果正式启用：至少建立一条真实记录链
   - 如果暂缓：保留代码，不纳入发布承诺

## 7. 建议执行顺序

建议严格按以下顺序推进：

1. 阶段 0
2. 阶段 1
3. 阶段 2
4. 阶段 3
5. 阶段 4
6. 阶段 5

原因如下：

- 阶段 0 先固定口径，避免后续返工
- 阶段 1 先稳住当前最活跃变更区
- 阶段 2 再收结果可信度，提升验收质量
- 阶段 3 整理测试分层，降低发布前判断成本
- 阶段 4 再定级新能力，避免半成品能力混入正式承诺
- 阶段 5 最后统一发布验收

## 9. 风险与应对

| 风险 | 影响 | 应对方式 |
|------|------|---------|
| GUI 主链继续膨胀 | 后续修改成本快速上升 | 先做阶段 1，优先外提共享元数据与规则 |
| 文档口径继续漂移 | 版本判断混乱 | 阶段 0 统一边界和发布口径 |
| 元数据表达不统一 | 真实数据验收难复用 | 阶段 2 建立统一摘要口径 |
| 测试很多但发布时不会用 | 发布风险上升 | 阶段 3 明确验证入口分层 |
| 新能力状态不清 | 文档承诺超过实际 | 阶段 4 明确定级 |
| 收口过程中顺手扩需求 | 项目范围失控 | 严格遵守第 3 章边界，不做无关扩展 |
